**Deviations:** no /code-review (the orchestrator forbade it); I did the bug pass by hand. Partway through, the orchestrator changed the closing keywords (Refs #182 + Closes #139), so I re-read the body and checked it against that.

**Decisions not covered:** the red tests a nested test-install.sh whose expected behaviour is a Bail out! (exit 1). To read its output, it goes through a runner script that ends with `exit 0`. Functionally this masks the status like `|| true`, but it is not literally in the forbidden list of tap.sh. The skill does not say how to judge a red whose behaviour under test *is* a bail out: `tap_run` expecting 1 and `|| true` are both forbidden, so a wrapper is the only way left. I accepted it because I confirmed the red failure output was the intended old Bail out! line in both nested runs, not an unrelated crash, and because the pass depends on a stub marker that only the fixed code can print. I also had to decide how to judge CI cost. Measured: test-tap.sh went from 4 s to 22 s in CI, and takes about 2.5 min locally on macOS. The implementer's "3-11 min" was a local figure on a loaded machine.

**What the review found:** no blockers. One to-fix: the static guard only greps lines that contain `install.py`. It cannot see calls made through the `instalar()` wrapper, so a future must-succeed `instalar ...; tap_status "$c" 0` would bring back the bug and the guard would stay green. Suggestions: the SC2319 file-level disable no longer has any effect at the tip (shellcheck 0.11.0 is clean without it); the tap.sh header could list the exit-0 runner pattern; the skip could be keyed on a kit marker.

**Proposal:** review-pr (and the tap.sh header) should say how to test a nested test's Bail out! in a red. One option: a runner that ends with 0 is accepted, as long as the case checks a marker that only the code under test prints and the reviewer checks the red's nested output. Also tell reviewers to measure CI cost from the CI log timestamps of the `# file:` lines, not from local runs.
