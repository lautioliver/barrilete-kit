**Deviations:** /code-review was not invoked (the orchestrator said not to); I did a manual pass from the review worktree. The end-to-end red.sh probe ran in a throwaway local clone in the scratchpad, not in the review worktree, so it could not disturb the test run going on in the background there. I only ran things on bash 3.2: there is no bash 5 on this machine, so for that I rely on the green CI.
**Decisions not covered:** how to prove a red-classification hole. The skill says how to check the PR's own red, not how to show that a crash pattern turns into a valid red. I made a disposable commit with a crash-in-assertion test and ran the trusted red.sh on it (exit 0). Also, whether a sanctioned opt-out idiom (`ec ... -eq 0`) is a blocker or a person's decision: I classified it as to fix and left the decision to the person.
**What the review found:** 2 blockers. (1) A status 1 or 2 crash inside a command or process substitution within `[`/`grep`/`diff`, or at the head of a pipeline into grep, still gives a valid red. red.sh exited 0 end to end on `[ "$(python3 missing.py)" = 3 ]`. (2) Without errtrace, functions and subshells are opaque. An undeclared function whose last command is `[` counts as an assertion because BASH_COMMAND leaks the inner command, and tap_assertions is a blanket waiver. Neither is in the documented limits. The direct cases, the TDD set (8/8) and migration fidelity (ids identical) were fine.
**Proposal:** review-pr could tell reviewers of test-helper or red-validation PRs to run a small adversarial corpus through the trusted red.sh in a scratch clone, as a standard step. red.sh could also warn when a red commit adds `tap_assertions`.
