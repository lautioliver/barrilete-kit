## What went well
- Checking the PR body's edit history (GraphQL userContentEdits) caught that the body had been overwritten with the body of the parallel PR #164 (Closes #150). Without it, the review would have assumed the body was the one from round 1.
- Reading the parallel PR's parser (red_report.py via the contents API, since `gh pr diff 164` fails above 300 files) made the cross-PR compatibility concrete: the TAP 14 `\#` escape is not undone by #164.
- A minimal script on tap.sh showed the fail-open (a missing python script as a valid red) instead of arguing it in the abstract.

## What went wrong or cost time
- `gh pr diff` fails on PRs with more than 300 files (corpus): use `gh api contents?ref=<sha>` for specific files.
- `/code-review` could not be used through the Skill tool (it acts on the orchestrator's checkout): the pass was done by hand.

## Proposal for the skill
- review-pr: in the conventions step, check that the PR body still says `Closes #<its issue>` (gh pr view --json closingIssuesReferences) and look at the body edit history when there are several PRs in parallel in the same epic.
- review-pr: when the PR implements less than an ADR says and documents it only in a code comment, treat it as a business-rule change that needs a person (it is not a "to fix").
